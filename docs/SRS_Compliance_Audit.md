# SIRI Education — SRS Compliance Audit

**This is a dated, one-time snapshot, not a continuously updated tracker.** It reflects the state of the repository as of 2026-07-19 against `docs/SRS.md` as it existed then. Features shipped after that date are not reflected here — cross-check any specific finding against current code/tests before treating it as still true, and prefer this document's own §7 (Recommended Implementation Roadmap) and §8 (Uncertainties and Decisions Needed) as the durable, actionable parts rather than the completion percentages, which will drift.

**Scope:** Full repository vs. `docs/SRS.md` (30,095 lines, Book 1 Ch.1–9 + Book 2 Ch.1–2,4–27), as of the date above. Read-only audit; no code, schema, config, docs, or tests were modified as part of producing these findings. 13 parallel domain agents traced entry point → authorization → validation → service → persistence → UI → side effects → tests for their assigned chapters; Book 1 was read in full for cross-cutting context, followed by synthesis into this report.

**Methodology note:** Book 2's own table of contents (SRS.md ~lines 3736–3837) does not match the actual chapter titles/content that follow it, and an entire chapter — **Book 2 Chapter 3 "Instructor Management"** — is missing from the SRS document itself (Book 2 jumps from Chapter 2 straight to Chapter 4). Both are flagged as documentation defects rather than silently worked around. Instructor-onboarding requirements were reconstructed from Book 1 §6.4–6.5 and §9.6 instead. The SRS also describes an `FR-`/`BR-`/`VR-` requirement-ID scheme in its Book 2 introduction that is never actually applied to any requirement in the document body — this audit assigns its own stable `SRS-<chapter>-<n>` IDs throughout, as instructed.

### The five most important blockers to a shippable product, in order

1. **Instructors cannot be paid.** The withdrawal/settlement pipeline is genuinely well-built, but the only "Paid" transition path is RazorpayX auto-payout, which is disabled pending external account activation, and there is no manual "mark paid" fallback (which the SRS itself explicitly permits for V1). Money accumulates; it never leaves the platform.
2. **Wallet cannot be used for its two core purposes.** There is no recharge flow (button says "Coming soon") and no way to pay for a lesson with wallet balance — despite the ledger core underneath being financially sound (atomic, idempotent, append-only).
3. **Several governed business rules are configured but silently unenforced.** "One free demo per instructor," the cancellation-refund window, the reschedule limit, per-country feature flags, demo/waitlist feature flags, and session idle-timeout all have live admin settings that no code path ever reads. This is a repeating pattern across five different domains, not five isolated bugs.
4. **There is no support/dispute case system and no student-instructor messaging at all** — only a one-way contact form exists where the SRS specifies a full case-management module.
5. **Operational readiness is thin:** no backup strategy, no active APM (Pulse is installed but never wired up), no automated queue/scheduler alerting, and no suspicious-activity/compliance-monitoring layer.

Against this, the financial core (booking concurrency, payment webhook idempotency, wallet ledger integrity, instructor-compensation isolation from student pricing) is unusually mature and well-tested — better than the surrounding product surface. The gap is concentrated in unfinished user journeys and unenforced configuration, not in financial-correctness engineering.

## 3. End-to-End Journey Gaps

**Guest/Public visitor.** Starts at the public site (home/about/blog/FAQ/contact — all real CMS-backed pages with correct SEO fallback chain and sitemap generation) and can reach a fully populated, SEO-indexed instructor public profile with real reviews and a verified badge. It breaks down in two places: no localized price is ever shown before the guest commits to registering (SRS-9-5/GAP-024), and there's no redirect layer to preserve SEO equity if a page slug changes (SRS-22-16/GAP-036). The guest→instructor-applicant path (apply, KYC, admin review, approval) is fully wired end-to-end and is one of the best-implemented journeys in the product.

**Student.** Registration → email verification → dashboard → learning goals → instructor discovery → demo booking → paid booking → lessons → homework → reviews is real and mostly solid. It fails at several concrete points: a student can book unlimited free demos with the same instructor (SRS-11-9/GAP-004, Critical); wallet cannot actually be recharged or used to pay for a lesson (SRS-13-6/13-7/GAP-002/003, Critical); cancellations always refund 100% regardless of policy and reschedules are unlimited (GAP-005/006); homework has no due-date reminders and cannot receive file attachments in either direction (GAP-020/022); there is no waitlist to join when no slot is available (GAP-018); and if a student ever has a problem, there is no support case to open — only a one-way contact form (GAP-016).

**Instructor.** Application → KYC → admin approval → availability setup → teaching → homework → earnings is solid through completion. It breaks down at the money: earnings accrue correctly and withdrawal requests work, but the only path to actually receiving money (RazorpayX auto-payout) is disabled pending external account activation, and there is no manual fallback (GAP-001, Critical) — instructors can accumulate a balance they can never withdraw. Availability management also has a real operational hole: editing or deleting a window that overlaps confirmed bookings produces no warning at all (GAP-019).

**Administrator.** User/role/permission management, CMS, settings, and reporting are all genuinely mature — permission-aware, masking-aware, and mostly audit-logged. Three gaps stand out: nothing stops an admin from deactivating or demoting the very last Super Admin (GAP-010); Payment settings changes are the one settings category with zero audit trail despite being explicitly named high-impact by the SRS (GAP-009); and there's no compliance/suspicious-activity monitoring layer at all (GAP-015), so admins have no systematic way to see fraud/abuse patterns forming.

**Background/operations.** Financial jobs (payment webhooks, wallet ledger, settlement batches) are idempotent, transaction-safe, and concurrency-tested — genuinely strong. Everything downstream of "is it correct" is thinner: failed jobs can be seen but not retried from the UI (GAP-034), there's no automated alerting on queue backlogs or scheduler stalls (GAP-035), no backup strategy exists (GAP-032), and the one APM tool already installed (Pulse) was never activated (GAP-033).

## 4. Cross-Cutting and Non-Functional Gaps

- **Authentication & authorization:** Solid Spatie-permission model, correctly enforced `Gate::before()` for super_admin only — but the last-super-admin safeguard is missing (GAP-010) and session idle-timeout is decorative (GAP-012).
- **Privacy & data exposure:** Instructor compensation is genuinely never exposed to students (verified across the Payments/Earnings audit); student review identity masking is real and computed fresh. No violations found here.
- **Security & abuse prevention:** This is the weakest cross-cutting area — no fraud-detection layer, no compliance-monitoring layer, and the one named binding fraud vector in the audit brief (repeat free demos) is unenforced (GAP-004/014/015).
- **Transactions, concurrency & idempotency:** The strongest area in the entire codebase. Real multi-process concurrency test suites exist for booking, payment, and earnings; wallet ledger and payment-webhook idempotency are both DB-constraint-backed, not just application-level checks.
- **Localization, currency & timezone:** UTC storage and browser-based timezone detection exceed the SRS's own ambition; the notification-timezone bug (GAP-030) and dead country-feature-flags (GAP-029) are the real gaps.
- **Accessibility & responsive UX:** Not independently audited at depth (out of scope for a backend-focused pass) — flagged as a genuine unknown, see Uncertainties.
- **Performance & database indexes:** Indexes on high-volume tables are present and correct; no CDN/edge caching, cache/queue defaults are `database` not `redis` (low priority — noted, not separately gapped).
- **Queue reliability & failed-job handling:** Idempotent and retryable, but not retryable _from the admin UI_ (GAP-034) and not alerted automatically (GAP-035).
- **Monitoring, audit logs & operational dashboards:** Audit logging is broad but has real holes (Payment settings, correlation ID, compliance monitoring). Pulse is installed but inert (GAP-033).
- **Backup, recovery & retention:** No backup strategy exists at all (GAP-032); no data-retention policy/purge mechanism exists (SRS-B1-11).
- **Deployment & production configuration:** Redis present in env template but not wired as default; `APP_DEBUG=true` in the example file (both low severity, standard Laravel convention).
- **Test coverage & CI enforcement:** Every domain audited had substantial, real feature/unit tests (not fabricated) — independently confirmed via targeted `--filter` runs by several agents (Reviews: 25/25 + 34/34 + 13/13 passing). No CI config file was found in the repo to independently verify enforcement — flagged as an uncertainty below.

## 6. SRS Deviations and Scope Conflicts

1. **"Refund follows configured cancellation window" (SRS 11.24) vs. code:** `BookingSettings::cancellation_window_hours` is a real, admin-editable setting that is never read by any refund logic — every cancellation refunds 100% to wallet regardless of timing.
2. **"Reschedules limited to a configurable maximum" (SRS 11.26) vs. code:** same pattern — `reschedule_limit` exists, is never read; students can reschedule without limit.
3. **"One free demo lesson per instructor per student" (SRS 11.13/11.39, and named explicitly in this audit's binding context) vs. code:** `FreeDemoType::rules()` is empty; the only duplicate check rejects an identical exact time slot, not a repeat demo with the same instructor at a different time.
4. **"Do not silently skip lessons in a recurring booking; require the student to choose alternatives before confirmation" (SRS 10.18) vs. code:** `bookRecurring()` does exactly the opposite — books every available occurrence and reports failures after the fact.
5. **"Version 1 may support manual payout processing... admin marks payout as paid" (SRS 15.31) vs. code:** the codebase deliberately, architecturally forecloses this exact V1-sanctioned fallback — there is no manual mark-paid action anywhere, and the only path to "Paid" is a currently-disabled external provider.
6. **"Notification times display in the recipient's local timezone" (SRS 21.13) vs. code:** every booking notification uses the _student's_ stored timezone for both the student and the instructor.
7. **"Teaching languages" modeled per Subject (SRS 4.14) vs. code:** languages are attached to the instructor, not the subject — a deliberate, documented design choice, but a real deviation from the SRS text.
8. **Chapter 5's entire Curriculum/Roadmap/Competency/Prerequisite engine (SRS 5.5-5.22)** has no code at all — the project's own `docs/archive/reports/academic-master-foundation.md` explicitly lists this as "not built yet," which is an honest admission but still means this large SRS chapter is currently 0% implemented.
9. **"No 'revenue' total exists anywhere... never summed, never cross-currency" (explicit code comment in `FinanceOverview.php`) vs. SRS 19.19's Critical-priority Revenue Report requirement** — a deliberate, reasoned decision to avoid fabricating a currency-ambiguous metric, but a real compliance gap against the SRS text as written.
10. **Book 2's own table of contents (SRS.md ~3736-3837) does not match the chapter content that follows it**, and **Book 2 Chapter 3 "Instructor Management" is entirely absent from the document** — both are defects in the SRS itself, not the code, but they materially affected this audit's ability to cite a single authoritative source for instructor-lifecycle requirements (Book 1 §6.4-6.5/§9.6 were used instead).

### Phase 1 — Financial correctness, security, and unenforced business rules (no new user-facing modules)

- **Closes:** SRS-15-14, SRS-13-6, SRS-13-7, SRS-11-9, SRS-11-20, SRS-11-22, SRS-20-18, SRS-23-7, SRS-23-6, SRS-1-23, SRS-2-20, SRS-10-12, SRS-7-11, SRS-7-1/12, SRS-27-27, SRS-27-29, SRS-26-2.

- **Dependencies:** none — this phase only wires existing settings/data to enforcement points and adds guards; no new domain models needed except a minimal manual-payout action and a homework-reminder job.
- **In scope:** enforcement of every "setting exists but is never read" finding; the one-demo-per-instructor rule; last-super-admin guard; session idle-timeout enforcement; student account-lifecycle write path; manual instructor payout fallback; wallet recharge + wallet-as-lesson-payment; homework reminders; backup strategy; Pulse activation.

- **Acceptance criteria:** every listed setting has a corresponding enforcement test; concurrency/idempotency regression suite still green; an instructor can complete a full withdrawal-to-paid cycle without RazorpayX.
- **Key risks:** manual-payout fallback must preserve the same financial rigor (audit trail, no double-pay) as the rest of the earnings pipeline — this is the highest-risk item in the phase.

- **Closes:** SRS-25-1/2/5/6/7, SRS-17-11, SRS-10-25/SRS-2-12/16/SRS-20-6, SRS-20-17/21-11, SRS-9-5, SRS-14-14/15/16, SRS-6-5, SRS-7-3/8, SRS-8-4/8-10, SRS-B1-9/14, SRS-24-11.
- **Gaps:** GAP-014 through GAP-018, GAP-022 through GAP-025, GAP-029, GAP-036, GAP-037, GAP-038, GAP-040, GAP-041.
- **Dependencies:** Phase 1's manual-payout and enforcement work should land first so support-case volume from those categories doesn't spike before the case system exists.
- **In scope:** support/dispute case system; student-instructor messaging (can share infra with support cases); waitlist; country-level feature-flag enforcement; localized pricing on discovery; homework resource library and reconnection to learning plans; basic recommendation sections; minimal fraud/compliance monitoring; invoice/receipt generation; real SMS/WhatsApp provider.

- **Acceptance criteria:** a student can open, track, and receive a resolution on a support case; an instructor can message a student post-booking under the same eligibility rules as the SRS describes; a country can be feature-flagged independently of the global toggle.
- **Key risks:** support-case and messaging modules are both XL-effort and share no existing foundation — likely the largest single investment in the roadmap.

### Phase 3 — Required integrations, async processing, and remaining reporting/analytics

- **Closes:** SRS-15-3/7, SRS-17-9, SRS-12-11 (recording), remaining export-action gaps, search analytics/recently-viewed, KPI snapshotting.

- **In scope:** demo-to-paid conversion incentive; admin-editable notification templates; meeting recording capture pipeline; search/profile-view analytics event capture; admin-editable robots.txt; redirect management; recurring-lesson and instructor-utilization reports.
- **Out of scope:** Curriculum/Roadmap/Competency engine (Book 2 Ch.5) — recommend treating as its own major initiative given zero existing code, not a "phase" item.

### Phase 4 (separate initiative, not sequenced above) — Academic Curriculum/Roadmap/Competency Engine (SRS Ch.5, parts of Ch.4)

This is large enough (Curriculum, Module, Topic-under-Module, Competency, Prerequisite, Learning Outcome, versioning/publishing) that it should be scoped and approved as its own initiative rather than folded into the phases above, given it's currently 0% implemented and touches Learning Plans, Homework, and Reporting once built.

## 8. Uncertainties and Decisions Needed

1. **Is the manual instructor-payout fallback (SRS 15.31) still wanted, or is the product committed to RazorpayX-only?** The codebase's current design is a deliberate, documented, financial-integrity-motivated choice to forbid any manual "mark paid" path. Reversing that is a real architectural decision, not just a bug fix. _Requires product-owner approval before Phase 1 implementation._
2. **Is "one free demo per instructor" still the intended rule, or has it quietly changed?** It's stated explicitly in this audit's binding context and in SRS 11.13/11.39, but the code has never enforced it, which — this far into development — could mean either an oversight or an intentional (undocumented) relaxation. _Needs confirmation before building GAP-004._
3. **Should `cancellation_window_hours` and `reschedule_limit` actually gate behavior, or were they deliberately left inert as placeholders for a future release?** No `docs/decisions.md` entry documents either as intentionally deferred — this looks like an oversight, but should be confirmed rather than assumed.
4. **What should the "Revenue Report" (SRS 19.19) actually mean** given the codebase's own documented objection (no cross-currency-safe definition exists)? This needs a product/finance decision on what "revenue" means in a multi-currency, wallet-mediated marketplace before engineering can build it.
5. **Is the Curriculum/Roadmap/Competency engine (Book 2 Ch.5) still in scope for the current release, or has it been quietly descoped?** It has zero code and is explicitly called out in the project's own `docs/archive/reports/academic-master-foundation.md` as deferred — but that's a phase-doc statement, not a `docs/decisions.md` entry, so it's not a formally approved deferral.
6. **Accessibility and CI enforcement were not deeply audited** — a proper WCAG-level pass and a check for automated CI test-gating (no CI config file was found in the repo during this pass) are both open items that need separate, dedicated verification.
7. **The Book 2 documentation defects (stale table of contents, missing Chapter 3)** should be corrected in `docs/SRS.md` itself so future audits and engineering work have a single reliable source — this is a documentation fix, not a code change, and was outside this audit's read-only mandate to perform directly.

## Recommendation

**Phase 1** (above) is the recommended next implementation phase. It closes the Critical/High financial-integrity and security gaps (unpayable instructors, missing wallet payment, unenforced demo/cancellation/reschedule rules, last-super-admin safeguard, unenforced session timeout) without requiring any new domain modules, and every item in it is a bounded, well-understood fix rather than a ground-up build. Product-owner approval is required before writing the Phase 1 implementation prompt (see Uncertainties #1–3 above).
